# Data dictionary and ownership

All `tenant_id` values are UUIDs. `id` is a UUID surrogate generated by PostgreSQL unless otherwise stated. A composite `(tenant_id,id)` primary key is used for each versioned root. All cross-table domain references are composite tenant-scoped foreign keys. `valid_during` is a half-open `tstzrange`; `row_version` increments on update. Root changes write `platform.entity_revision`, `platform.audit_event`, and `platform.outbox_event` in the same transaction.

## Key columns and rules

- `code`: human-facing tenant-local identifier; uniqueness is explicitly scoped by tenant (and parent where appropriate).
- `owner_id`, `sponsor_id`, `chair_id`, `recorded_by`: tenant membership foreign keys. Membership can later be inactive without destroying historical attribution.
- `source_system_id` and `external_transaction_key`: ERP/feed identity used for idempotent imports.
- `row_version`: optimistic concurrency token. Database trigger ignores application attempts to choose the next value.
- `valid_during`: business effective interval. `entity_revision.recorded_during` records when a row version was held by this database.
- `baseline.recorded_during`: when that approved baseline was known as current. It closes when overlapping valid time is superseded.
- `decision.subject_type`/`subject_id` and `baseline_item.item_type`/`item_id`: deliberate polymorphic references; use command-service validation plus audit because a single physical FK is not possible.

## Indexes

Primary/unique indexes cover tenant-first lookups. Additional indexes target reverse FKs, latest assessments and decisions, actuals by initiative/date, capacity by pool/month, pending outbox events, unprocessed inbox messages, and GiST temporal overlap lookups. Review query plans with production data before adding broader reporting indexes; analytic replicas or materialized views should handle wide portfolio dashboards.
